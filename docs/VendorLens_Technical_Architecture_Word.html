1. Architecture at a glance

VendorLens manages a supplier from initial case creation through document intake, AI-assisted review, deterministic compliance, and a final human decision. The browser never calls an AI provider directly. FastAPI owns validation, redaction, AI orchestration, retrieval isolation, compliance, and audit recording.

2. Workflow and data storage

Implemented onboarding sequence

  1. Create a supplier case using legal name, country, and optional contact email.
  2. Upload exactly one registration, tax, and insurance document. Supported formats are selectable-text PDF and UTF-8 text, with a default 10 MB maximum.
  3. Extract source text synchronously and retain explicit [Page N] markers.
  4. Redact detected PII, extract structured fields, select canonical cross-document values, and construct a vector index.
  5. Review or correct fields, ask cited supplier-specific questions, and run six deterministic compliance rules.
  6. Approve only when every rule passes, or reject with an auditable reason. Approval creates a deterministic mock ERP reference.

Source-of-truth rule. PostgreSQL owns business state. ChromaDB can be reconstructed from supplier documents and is never treated as the authoritative record. Reprocessing replaces derived fields and vectors; document deletion clears stale derived data.

Document extraction and privacy boundary

PDF text is extracted with PyMuPDF; text files are decoded as UTF-8. Image-only or unreadable PDFs fail visibly because OCR is not implemented. Before AI calls, regular-expression rules replace detected GSTIN, PAN, CIN, email, phone, and bank-account values with stable typed placeholders such as [EMAIL_1]. Repeated values reuse the same placeholder.

The redacted form is used for structured extraction, embeddings, and grounded Q&A. After validated structured extraction, placeholders may be restored before canonical fields are saved to PostgreSQL for reviewer use. Raw extracted text also remains in PostgreSQL, so database access must be treated as sensitive.

Canonical structured fields

The extraction model returns a schema-validated document type plus field name, value, page, and confidence at temperature zero. Null-like values are removed. Values below 0.75 confidence, classification mismatches, or invalid page references require review. Repeated fields are ranked by authoritative source—tax documents for tax identifiers and insurance documents for insurer/expiry data. Conflicts keep the preferred value but force human review.

3. Retrieval-augmented generation (RAG)

The RAG design has two controlled phases: index construction when all three supplier documents are processed, and supplier-scoped retrieval when a question is asked.

Chunking methodology

ParameterImplemented behaviorReason
SegmentationSplit first on [Page N]; chunks never cross pagesPreserves unambiguous page citations
Tokenizertiktoken.encoding_for_model(); fallback to cl100k_baseModel-aligned, deterministic token counts
WindowMaximum 500 tokensBalances local context with retrieval precision
Overlap75 tokens; 425-token strideRetains context around window boundaries
MetadataSupplier, document, filename, page, chunk index, token countIsolation, traceability, and citation mapping

Retrieval and answer acceptance

The redacted question is embedded using the same embedding model family as indexed chunks. Chroma queries the supplier_chunks_v1 HNSW cosine collection with a mandatory exact supplier_id metadata filter. Only the nearest four results are requested, and results with cosine distance greater than 0.72 are discarded.

Eligible evidence is sent to the answer model as short labels such as chunk_1, with source filename and page. The model returns a structured answer, an information_found flag, and cited labels. The backend accepts the answer only when the flag is true and at least one label exists in the retrieved set. Otherwise, it returns the fixed safe response: “Information not found in uploaded supplier documents.”

Isolation and grounding. Filtering occurs inside the vector query before ranking results are consumed. Valid model labels are mapped back to the real filename, page, excerpt, and internal chunk ID. This prevents cross-supplier retrieval and rejects uncited model answers at the application boundary.

Observability and evaluation

Prometheus records bounded-label HTTP, dependency, AI latency/token, processing, retrieval, compliance, and decision metrics. Langfuse tracing is optional and metadata-only by default; content capture requires an explicit setting. Promptfoo plus controlled multi-supplier document packs evaluate extraction, citation accuracy, guarded not-found behavior, latency, and supplier isolation.

Current implementation boundaries

  • Synchronous processing is designed for demonstration-scale workloads, not a distributed job architecture.
  • OCR, scanned-document support, malware scanning, and managed object storage are not implemented.
  • The ERP boundary is a deterministic local mock rather than a production integration.
  • Production authentication, authorization, and tenant isolation are not present.
  • Embedded ChromaDB and local uploads suit a single application instance; horizontal scaling needs externalized storage and coordinated indexing.
  • Human review remains mandatory: semantic retrieval and citation gates reduce unsupported answers but do not eliminate model interpretation errors.
